# Annals data model

## Overview

The schema has two layers:

- **Canonical:** `nodes` and `sources`. These contain the user's tree and source
  material and must be backed up.
- **Derived:** `search_units`, `search_fts`, and `index_metadata`. These may be
  recreated from canonical rows by `annals reindex`.

SQLite integer primary keys are stable identities within a library. Paths and
breadcrumbs are derived strings and must not be used as foreign keys.

The DDL below is a concrete baseline. Migration files should contain the actual
schema so database creation and upgrades use the same path.

## Connection setup

Apply these settings on every connection as appropriate:

```sql
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA journal_mode = WAL;
```

`journal_mode` persists, but setting it when opening a library makes the
expectation explicit. Do not depend on foreign keys being enabled by default.

## Baseline schema

```sql
CREATE TABLE schema_migrations (
    version     INTEGER PRIMARY KEY,
    applied_at  TEXT NOT NULL
);

CREATE TABLE nodes (
    id          INTEGER PRIMARY KEY,
    parent_id   INTEGER
                    REFERENCES nodes(id)
                    ON DELETE CASCADE
                    DEFERRABLE INITIALLY DEFERRED,
    kind        TEXT NOT NULL
                    CHECK (kind IN ('topic', 'source')),
    title       TEXT NOT NULL
                    CHECK (length(trim(title)) > 0),
    body        TEXT NOT NULL DEFAULT '',
    position    INTEGER NOT NULL DEFAULT 0
                    CHECK (position >= 0),
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);

CREATE INDEX nodes_by_parent
    ON nodes(parent_id, position, id);

CREATE UNIQUE INDEX nodes_unique_child_position
    ON nodes(parent_id, position)
    WHERE parent_id IS NOT NULL;

CREATE UNIQUE INDEX nodes_unique_root_position
    ON nodes(position)
    WHERE parent_id IS NULL;

CREATE TABLE sources (
    node_id      INTEGER PRIMARY KEY
                     REFERENCES nodes(id) ON DELETE CASCADE,
    locator      TEXT,
    media_type   TEXT,
    checksum     TEXT,
    captured_at  TEXT
);

CREATE TABLE search_units (
    id               INTEGER PRIMARY KEY,
    node_id          INTEGER NOT NULL
                         REFERENCES nodes(id) ON DELETE CASCADE,
    unit_no          INTEGER NOT NULL
                         CHECK (unit_no >= 0),
    unit_kind        TEXT NOT NULL
                         CHECK (unit_kind IN ('node', 'passage')),
    title            TEXT NOT NULL,
    normalized_title TEXT NOT NULL,
    breadcrumb       TEXT NOT NULL,
    normalized_path  TEXT NOT NULL,
    text             TEXT NOT NULL,
    start_byte       INTEGER,
    end_byte         INTEGER,
    content_hash     TEXT NOT NULL,
    indexer_version  INTEGER NOT NULL,
    CHECK (
        (unit_kind = 'node' AND start_byte IS NULL AND end_byte IS NULL)
        OR
        (unit_kind = 'passage'
         AND start_byte IS NOT NULL
         AND end_byte IS NOT NULL
         AND start_byte >= 0
         AND end_byte >= start_byte)
    ),
    UNIQUE (node_id, unit_no)
);

CREATE INDEX search_units_by_node
    ON search_units(node_id, unit_no);

CREATE INDEX search_units_by_normalized_title
    ON search_units(normalized_title, node_id);

CREATE INDEX search_units_by_normalized_path
    ON search_units(normalized_path, node_id);

CREATE VIRTUAL TABLE search_fts USING fts5(
    title,
    breadcrumb,
    text,
    content = 'search_units',
    content_rowid = 'id',
    tokenize = 'unicode61 remove_diacritics 2',
    prefix = '2 3 4'
);

CREATE TRIGGER search_units_after_insert
AFTER INSERT ON search_units
BEGIN
    INSERT INTO search_fts(rowid, title, breadcrumb, text)
    VALUES (new.id, new.title, new.breadcrumb, new.text);
END;

CREATE TRIGGER search_units_after_delete
AFTER DELETE ON search_units
BEGIN
    INSERT INTO search_fts(search_fts, rowid, title, breadcrumb, text)
    VALUES ('delete', old.id, old.title, old.breadcrumb, old.text);
END;

CREATE TRIGGER search_units_after_update
AFTER UPDATE ON search_units
BEGIN
    INSERT INTO search_fts(search_fts, rowid, title, breadcrumb, text)
    VALUES ('delete', old.id, old.title, old.breadcrumb, old.text);
    INSERT INTO search_fts(rowid, title, breadcrumb, text)
    VALUES (new.id, new.title, new.breadcrumb, new.text);
END;

CREATE TABLE index_metadata (
    key    TEXT PRIMARY KEY,
    value  TEXT NOT NULL
);
```

Timestamps are UTC RFC 3339 text generated by Rust. `checksum` and
`content_hash` should include an algorithm prefix, such as `sha256:...`, so the
algorithm can change without ambiguity.

`nodes.body` is the canonical text for both a topic view and an inline or
captured source. `sources` adds leaf-specific provenance. A locator may be a URL,
filesystem path, citation, or other opaque reference; its interpretation belongs
to import/open commands, not the tree model.

The title is a short navigation label, while the body is the view or source
text. Titles do not have to be globally or locally unique. CLI commands that
accept a path must report ambiguity and ask for a stable node ID rather than
silently choosing one.

## Why external-content FTS5

`search_units` stores the complete derived unit and its ownership and offset
metadata. `search_fts` indexes its searchable columns while using the unit ID as
the FTS row ID. The three triggers keep both representations synchronized for
normal writes.

The FTS table is still derived. If trigger state or an index format is ever in
doubt, repair it from `search_units` with:

```sql
INSERT INTO search_fts(search_fts) VALUES ('rebuild');
```

The application should not write directly to `search_fts` except through FTS5
maintenance commands. Unit insertion, replacement, and deletion goes through
`search_units` so the triggers see every change.

## Enforcing tree invariants

Foreign keys enforce parent existence and cascading subtree deletion. Partial
unique indexes enforce sibling order. Other cross-row conditions are clearest
as application checks performed in the same transaction as the mutation.

Before attaching or moving a node under a parent, verify that the parent is a
topic. Before changing a topic to a source, verify it has no children. Source
creation must insert both `nodes` and `sources`; source deletion cascades the
metadata row.

Before moving `:node_id` below `:new_parent_id`, reject a destination inside the
moving subtree:

```sql
WITH RECURSIVE subtree(id) AS (
    SELECT id FROM nodes WHERE id = :node_id
    UNION ALL
    SELECT n.id
    FROM nodes AS n
    JOIN subtree AS s ON n.parent_id = s.id
)
SELECT EXISTS (
    SELECT 1 FROM subtree WHERE id = :new_parent_id
);
```

Self-parenting is included in this check. Run it before the update while the
write transaction is held, so another writer cannot invalidate the result.

`annals validate` should independently walk all parent chains and report cycles
in case a database was created by an older or external writer. It should also
report:

- source nodes with children;
- source nodes without a `sources` row;
- `sources` rows whose node kind is not `source`;
- topic leaves, as incomplete-tree warnings;
- stale or invalid search-unit ranges and hashes.

If protecting against arbitrary third-party SQL writers becomes important,
small triggers can duplicate the source/parent checks. For the initial CLI,
centralized repository transactions plus `validate` are easier to understand
and test than a large trigger program.

## Traversal queries

All roots in display order:

```sql
SELECT *
FROM nodes
WHERE parent_id IS NULL
ORDER BY position, id;
```

One subtree in depth-first path order can be assembled with a recursive CTE:

```sql
WITH RECURSIVE subtree(id, parent_id, depth, sort_path) AS (
    SELECT id, parent_id, 0, printf('%020d', position)
    FROM nodes
    WHERE id = :root_id

    UNION ALL

    SELECT n.id,
           n.parent_id,
           s.depth + 1,
           s.sort_path || '/' || printf('%020d', n.position)
    FROM nodes AS n
    JOIN subtree AS s ON n.parent_id = s.id
)
SELECT n.*, subtree.depth
FROM subtree
JOIN nodes AS n USING (id)
ORDER BY subtree.sort_path;
```

The zero-padded sort path is query-local, not persisted. Breadcrumb text is
generated by Rust from ancestor titles when indexing. A node move or ancestor
title change therefore regenerates units for the affected subtree.

## Search query shape

The FTS input must be constructed from parsed user terms. Ordinary search text
should be quoted/escaped as literals; advanced FTS syntax, if ever exposed,
should be an explicit mode.

A subtree-scoped query has this general shape:

```sql
WITH RECURSIVE scope(id) AS (
    SELECT :scope_id
    UNION ALL
    SELECT n.id
    FROM nodes AS n
    JOIN scope AS s ON n.parent_id = s.id
)
SELECT su.id AS unit_id,
       su.node_id,
       su.unit_no,
       su.title,
       su.breadcrumb,
       su.start_byte,
       su.end_byte,
       bm25(search_fts, 8.0, 2.0, 1.0) AS rank,
       snippet(search_fts, 2, '[', ']', '…', 24) AS snippet
FROM search_fts
JOIN search_units AS su ON su.id = search_fts.rowid
JOIN scope ON scope.id = su.node_id
JOIN nodes AS n ON n.id = su.node_id
WHERE search_fts MATCH :fts_query
  AND (:kind IS NULL OR n.kind = :kind)
ORDER BY rank
LIMIT :candidate_limit;
```

FTS5 returns better BM25 matches as lower values, so sort ascending. The numeric
weights are a starting policy, not a schema guarantee. Fetch more candidates
than will be displayed so Rust has room to collapse repeated passages and
diversify branches.

An unscoped query omits the `scope` CTE and join. Exact ID and title lookups are
separate queries whose matches are merged ahead of or explicitly boosted over
the FTS candidates.

## Unit generation

For every node, the indexer receives its canonical title, body, kind, ancestor
titles, and stable ID. It emits units in a deterministic `unit_no` order.

- Short bodies emit one `node` unit. Its offset fields are null.
- Chunked bodies emit `passage` units with UTF-8 byte offsets into `nodes.body`.
- Empty bodies may emit a title-only `node` unit so the topic remains findable.
- Breadcrumbs exclude or include the current title consistently; including it
  is simple, but title weighting must account for the duplicate token.

Define `content_hash` over every input that affects the row, including title,
normalized title, breadcrumb, normalized path, unit text, offsets, and indexer
version. This lets `annals validate` compare stored units with freshly derived
values without relying on timestamps.

When replacing one node's units, delete and reinsert them in the same
transaction. Do not try to preserve search-unit IDs: they are derived identities
and are not exposed as durable CLI handles.

## Mutation recipes

### Insert

1. Begin an immediate transaction.
2. Resolve and validate the parent.
3. Allocate a sibling position.
4. Insert the node and, for a source, its source row.
5. Generate `search_units`.
6. Commit.

### Edit

Update canonical fields and `updated_at`. Regenerate the edited node's units.
If the title changed, regenerate units for all descendants because their
breadcrumbs changed.

Changing kind is explicit. Topic-to-source is valid only with no children and
must add a source row. Source-to-topic removes the source row and is allowed to
remain an incomplete topic leaf while editing.

### Move

1. Begin an immediate transaction.
2. Resolve the node and new parent.
3. Reject a source parent and a cycle.
4. Allocate the destination position and update `parent_id`.
5. Normalize the old or new sibling positions if necessary.
6. Regenerate units for the moved subtree because every breadcrumb changed.
7. Commit.

### Delete

Resolve and display the subtree before asking for confirmation. Once confirmed,
delete its root in an immediate transaction. `ON DELETE CASCADE` removes
descendant nodes, source rows, and search units; search-unit delete triggers
remove FTS entries. Deletion does not promote children.

### Reorder

Use spaced positions for the common case. To swap or compact positions under
the unique indexes, first move affected rows to unused temporary non-negative
positions, then assign their final positions, all in one transaction. Reordering
does not affect breadcrumbs or search units.

## Reindex transaction

The straightforward implementation is:

```sql
BEGIN IMMEDIATE;
DELETE FROM search_units;
-- Rust derives and inserts all current units here.
INSERT INTO search_fts(search_fts) VALUES ('rebuild');
INSERT INTO index_metadata(key, value)
VALUES ('indexer_version', :version)
ON CONFLICT(key) DO UPDATE SET value = excluded.value;
COMMIT;
```

The delete and inserts already fire FTS maintenance triggers; the final rebuild
is an intentional consistency pass from the complete external-content table.
On any error, roll back so the previous units and FTS index remain usable.

If startup finds no `indexer_version`, a different version, or missing units, it
should explain that reindexing is required. Canonical reads and exports can
still work; search should not pretend a known-stale index is complete.

## Migration policy

Use numbered, forward-only SQL migrations such as `0001_initial.sql`. The Rust
migration runner applies missing versions in order in one write transaction and
records their UTC timestamp in `schema_migrations`.

Schema rules:

- never edit an already released migration;
- reject schema versions newer than the executable supports;
- preserve node IDs through canonical migrations;
- prefer a full reindex after any tokenizer, chunker, breadcrumb, or FTS schema
  change;
- back up before a migration that rewrites canonical rows;
- run `PRAGMA foreign_key_check` after structural migrations.

There is no need for an ORM in the base implementation. Prepared SQL through
`rusqlite`, typed row conversion, and transaction-focused repository methods
keep the behavior visible and compact.
